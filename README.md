# Event WebAPI - микросервисы

Распределенная система управления событиями и бронированиями, построенная на базе микросервисов на ASP.NET Core с использованием PostgreSQL и Apache Kafka.

## Используемые технологии:
- .NET 10
- ASP.NET Core Web API
- PostgreSQL 16 (по отдельной БД на сервис)
- Apache Kafka (асинхронное взаимодействие)
- Entity Framework Core 10
- Swagger/OpenAPI
- Docker & Docker Compose

## Архитектура проекта и структура слоев

Система состоит из трех независимых микросервисов, каждый со своей базой данных:

### 1. Auth Service (Сервис аутентификации)
- **Порт:** 5003
- **База данных:** `users-db` (PostgreSQL, порт 5433)
- **Назначение:** Управление пользователями, аутентификация и выдача JWT-токенов
- **Основные функции:**
  - Регистрация и аутентификация пользователей
  - Генерация и валидация JWT-токенов
  - Хранение учетных записей пользователей

### 2. Events Service (Сервис событий)
- **Порт:** 5002
- **База данных:** `events-db` (PostgreSQL, порт 5434)
- **Назначение:** Управление событиями и бронированиями
- **Основные функции:**
  - CRUD операции с событиями
  - Создание бронирований
  - Проверка доступности мест
  - **Публикация событий в Kafka:** при создании бронирования публикует событие `BookingCreated`

### 3. Booking Service (Сервис бронирований)
- **Порт:** 5001
- **База данных:** `bookings-db` (PostgreSQL, порт 5435)
- **Назначение:** Асинхронная обработка бронирований
- **Основные функции:**
  - **Подписка на топик Kafka:** `booking-events`
  - Получение событий о созданных бронированиях
  - Асинхронное подтверждение бронирований в фоновом режиме
  - Управление статусами бронирований (Pending → Confirmed/Rejected)

### **Kafka:** localhost:9092
### **Базы данных:**
  - users-db: localhost:5433
  - events-db: localhost:5434
  - bookings-db: localhost:5435

## Поток данных (BookingConfirmed)
1. **Клиент создает бронирование:** отправляет POST-запрос в `Booking Service` (`POST /api/bookings/events/{eventId}`).
2. **Booking Service:**
   - Валидирует запрос и создает запись бронирования со статусом `Pending` (0) в `bookings-db`.
   - Возвращает клиенту `202 Accepted`.
3. **Фоновая обработка (`BackgroundBookingService`):**
   - Периодически опрашивает `bookings-db` на наличие записей со статусом `Pending`.
   - Меняет статус бронирования на `Confirmed` (1) и обновляет поле `ProcessedAt`.
   - **Публикует событие `BookingConfirmedEvent`** в Kafka.
4. **Events Service:**
   - Слушает топик Kafka через `KafkaEventConsumer`.
   - При получении события извлекает `EventId` и уменьшает количество доступных мест (`AvailableSeats`) у события в `events-db`.

## Основные методы для работы с Event
| Метод     | Эндпоинт                | Описание                                    | Ответ                                                             |
| --------- | ----------------------- |  ------------------------------------------ | --------------------------------                                  |
| GET       | `/api/events`           | Получение списока всех событий              | 200 OK: Возвращает объект PaginatedResult<EventResponse>          |
| GET       | `/api/events/{id}`      | Получение события по ID                     | 200 OK: Возвращает объект EventResponse для найденного события    |
| POST      | `/api/events`           | Создать новое событие                       | 201 Created: Событие успешно создано                              |
| PUT       | `/api/events/{id}`      | Обновление существующего события            | 200 OK: Возвращает обновленный объект EventResponse               |
| DELETE    | `/api/events/{id}`      | Удаление события по ID                      | 204 No Content: Событие успешно удалено. Тело ответа отсутствует  |

Модель Event (БД):
- ID (Guid): Уникальный идентификатор
- Title (string): Наименование события
- Description (string): Описание события
- TotalSeats (int): Общее количество мест
- AvailableSeats (int): Количество свободных мест
- StartAt (DateTime) ( UTC ): Дата начала события
- EndAt (DateTime) ( UTC ): Дата окончания события

Модель Event для создания:
- Title (string): Наименование события
- Description (string): Описание события
- TotalSeats (int) ( API ожидает UTC ): Общее количество мест
- StartAt (DateTime) ( UTC ): Дата начала события
- EndAt (DateTime) ( UTC ): Дата окончания события

Модель Event для обновления/удаления:
- ID (Guid): Уникальный идентификатор
- Title (string): Наименование события
- Description (string): Описание события
- TotalSeats (int): Общее количество мест
- StartAt (DateTime) ( UTC ): Дата начала события
- EndAt (DateTime) ( UTC ): Дата окончания события

Получение списка событий (с фильтрацией и пагинацией)
`GET /api/events`
Возвращает список событий, обернутый в объект пагинации. Все параметры являются опциональными.

Параметры запроса:
* title (string): Фильтрация по названию (частичное совпадение, регистронезависимо).
* from (DateTime) ( API ожидает UTC ): Выбирает события, начинающиеся не ранее этой даты.
* to (DateTime) ( API ожидает UTC ): Выбирает события, заканчивающиеся не позднее этой даты.
* page (int): Номер страницы (по умолчанию 1).
* pageSize (int): Количество элементов на страницу (по умолчанию 10).

## Основные методы для работы с Booking
| Метод     | Эндпоинт                        | Описание                                             | Ответ                                                                                            |
| --------- | ------------------------------  |  --------------------------------------------------- | -------------------------------------------------------------------------------------------------|
| GET       | `/api/bookings/{bookingId}`     | Получение конкретного бронирования                   | 202 Accepted. В теле возвращается объект брони, в заголовке Location, ссылка на статус брони     |
| POST      | `api/bookings/events/{eventId}` | Создание нового бронирования по Id события           | 202 Accepted. Объект бронирования                                                                | 
| POST      | `api/bookings/{bookingId}/`     | Отмена бронирования по id события и id бронированию  | 204 NoContent. Объект бронирования                                                               |


Модель Booking:
- ID (Guid): Уникальный идентификатор
- EventId (Guid): ID события, к которому относится бронь
- Status (Enum): Статус бронирования
- CreatedAt (DateTime) ( API ожидает UTC ): Время создания заявки
- ProcessedAt (DateTime?) ( UTC ): Время обработки фоновым сервисом

Статусы бронирования:
- Pending (0): Заявка создана и ожидает обработки 
- Confirmed (1): Бронирование успешно подтверждено 
- Rejected (2): Бронирование отклонено

## Обработка ошибок
В проекте реализована глобальная обработка исключений через Middleware. В случае возникновения ошибки сервер возвращает единообразный ответ
Типовые коды ответов:
* 400 Bad Request: Ошибки валидации (например, дата окончания раньше даты начала).
* 404 Not Found: Ресурс не найден в системе.
* 409 Conflict: Недостаточно мест на событие.
* 500 Internal Server Error: Непредвиденная ошибка на стороне сервера.  

## Фоновая обработка
В системе реализован BackgroundBookingService на базе BackgroundService, который взаимодействует с данными
- Раз в несколько секунд сервис опрашивает IBookingRepository на наличие записей со статусом Pending
- Для каждой найденной записи выполняется изменение статуса меняется на Confirmed 
- После обработки обновляется поле ProcessedAt
- Изменения сохраняются

## Примитивы синхронизации
1. **`Interlocked (CompareExchange)` - в модели `EventModel`**
   * **Зачем нужен:** Используется для реализации неблокирующего алгоритма изменения количества мест в методах `TryReserveSeats` и `ReleaseSeats`

2. **`SemaphoreSlim` - в сервисе `BookingService`**
   * **Зачем нужен:** Защищает критическую секцию в методе `CreateBookingAsync`. Выступает в роли асинхронного аналога `lock`. Он гарантирует атомарность всей цепочки бизнес-логики: *Получить событие -> Проверить места -> Зарезервировать место -> Сохранить событие -> Создать бронь*
